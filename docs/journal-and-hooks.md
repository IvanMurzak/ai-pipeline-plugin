# The event journal and its hooks

> Load-bearing contracts, loaded on demand. Follow each bullet's lockstep rules and bump the plugin `version` in `plugin.json` on any meaningful change (see `CLAUDE.md`).

Was `docs/ui-subsystem.md`. The **local dashboard is deleted** (plugin-thin
[`01-remove-local-ui.md`](../../.taskflow/2026-08-03-plugin-thin/01-remove-local-ui.md)
in the parent repo) — the app, its daemon, its supervisor, its launch hook and
`pipeline ui` are all gone, and the hosted dashboard is the UI. **What did not
go is the journal.** `<project>/.pipeline/.runtime/events.jsonl` was built for
that app and is still named after it in the environment variables, but it is
now `ux-v2`'s telemetry source: the outbox reads it, the uploader drains it,
and `pipeline logs` renders it. Everything below is the part of the old
document that describes the journal and the hooks that write it.

The schema itself lives in [`docs/events.md`](events.md).

**⚠ THE HOOK RELAYS ARE NOT IN THIS REPOSITORY (plugin-thin `p6`).** Every
`<cli>/src/hooks/…` path below names a file in **`github.com/IvanMurzak/pipeline`**
— the CLI's own repository, published as `@baizor/pipeline`, carried in the
parent monorepo as the submodule `public/package/pipeline`. What this plugin
ships is `hooks/hooks.json` (the registrations) and `hooks/run-hook.sh` (the
shim that resolves an absolute `pipeline` binary for the non-interactive
`/bin/sh` Claude Code runs hooks in). Each registration is
`run-hook.sh [--loud] hook <name>` and each `<name>` is a CLI subcommand:

| Registration | Subcommand |
|---|---|
| SessionStart (primary, `--loud`) | `pipeline hook session-relay` |
| SessionStart | `pipeline hook department-notifier-relay` |
| PreToolUse · PostToolUse · Stop · SubagentStop · Notification | `pipeline hook analytics-relay` |
| Stop · SubagentStop | `pipeline hook stats-relay` |
| UserPromptSubmit | `pipeline hook prompt-match-relay` |

So **a hook's version is the installed CLI's version, by construction** — the
skew that was possible while the plugin shipped both a CLI copy and the relays
cannot happen. It also means this plugin now genuinely REQUIRES
`bun add -g @baizor/pipeline`; the `--loud` SessionStart entry is what says so
when it is missing. Every lockstep rule below still applies — the files just
live one repository over, and a change to a relay is a change to the CLI.

**Write scope with respect to the consumer project: STRICTLY inside
`<project>/.pipeline/`.** The hooks only ever append to `.runtime/events.jsonl`
(plus the per-user bindings journal under `~/.claude/pipeline-ui/`). They never
touch consumer files.

Two layers, each with a single owner:

| Where | Who writes | What |
|---|---|---|
| `~/.claude/pipeline-ui/` | the hooks + `pipeline drive` | `active-mirror-bindings.jsonl` (issue #11 — append-only session→run bindings) |
| `<project>/.pipeline/.runtime/` | `/pipeline:run` + `pipeline drive` + the hooks | `events.jsonl` (append-only journal), `transcripts/<session>.offset` (token-counter cursors), `runs/<run_id>.alive` (liveness lockfiles) |

This split is load-bearing: the plugin install dir must stay read-only (see
"Path resolution rules" in the plugin `CLAUDE.md`), the bindings are per-user
because a session id is a user-level fact, and per-project events must travel
with the project (gitignored).

## Hard invariants

- **Worktrees resolve to their main repo.** A git worktree is NOT a separate project — its events land in the main repo's `.runtime/events.jsonl` with a `worktree:` tag on each event. Worktree detection logic in `apps/pipeline-cli/src/lib/event.ts` (the TS event writer `pipeline event` calls), `<cli>/src/hooks/analytics-relay.ts`, `<cli>/src/hooks/session-relay.ts`, and `<cli>/src/hooks/prompt-match-relay.ts` MUST stay in sync. If you change one, change the others — they all read `.git/commondir` the same way, and `<superrepo>/tests/cross-repo/resolve-parity.test.ts` fails when a copy drifts.
- **The run anchor is `pipeline-manager`; the worker is `step-executor` (legacy `pipeline-executor` tolerated).** The run is identified by the `pipeline-manager` spawn, not the per-step worker. The hook matches the manager with `MANAGER_SUBAGENT_RE = /^(?:[a-z0-9_-]+:)?pipeline-manager$/` and the worker with `WORKER_SUBAGENT_RE = /^(?:[a-z0-9_-]+:)?(?:step-executor|pipeline-executor(?:-(haiku|sonnet|opus))?)$/` (the legacy worker name + its long-removed per-tier suffix stay tolerated so in-flight/forked runs still bind). A worker spawn is **never** a run anchor — it only gets a mirror binding attributed to the owning run.
- **`/pipeline:run` is the canonical semantic emitter.** Hooks emit only what they're naturally positioned to know: `SessionStart` → `session.opened`; `PreToolUse` (manager Agent/Task spawn) → mirror binding write (issue #11) **+ RUN-LEVEL bypass START-half synthesis** (`pipeline.started` ONLY); `PostToolUse` → `tool.called` + RUN-LEVEL bypass **END-half synthesis** (`pipeline.completed`/`halted` ONLY), or the both-event fallback when `PreToolUse` never ran; `SubagentStop` (a `pipeline-manager` ends) → `manager.stopped`; `Stop` → `turn.usage`; `Notification` → `run.awaiting_input`. The `SubagentStop` hook is a **liveness signal**, NOT a re-derivation of the manager report — `/pipeline:run` already parses the report; emitting lifecycle from `manager.stopped` would be double-emission. The hooks NEVER synthesize `iteration.*` — the `pipeline-manager` self-emits those.
- **Bypass (Path-C) lifecycle synthesis is RUN-LEVEL, anchored on the manager, and SPLIT across PreToolUse/PostToolUse — keep it split.** The whole point is that a directly-spawned `pipeline-manager` (no `/pipeline:run`) is recorded as an **active** run while the manager is in-flight — so `pipeline.started` MUST be emitted at spawn time (`PreToolUse`), not deferred to the Agent's return; `pipeline.completed`/`halted` is the END half (`PostToolUse`). Both halves share one run_id — a deterministic UUIDv5 derivation of `tool_use_id` (`hookIdFromToolUseId`, `apps/pipeline-cli/src/lib/ids.ts`; never `newId()`, which is random by design). Path B is told apart by (1) the literal `run_id = …` line the supervisor writes into the manager prompt (`extractRunIdFromPrompt`), and (2) failing that, comparing our tool_use_id-derived id against the journal's most-recent matching `pipeline.started`/`iteration.started.run_id` (different id ⇒ supervisor owns it ⇒ stay silent). `journalHasPipelineStarted(runId)` chooses split-END vs both-event fallback in `PostToolUse`. If you change the split, the run_id derivation, the manager/worker regexes, or the discriminator, update `synthesizeBypassStart`/`synthesizeBypassEnd`/`synthesizeBypassRun` in `<cli>/src/hooks/analytics-relay.ts`, `docs/events.md` (Path-C section), and `tests/hook-pretool-binding.test.ts` + `tests/hook-bypass-detection.test.ts` in lockstep. A Path-C run killed between the two halves leaves a `pipeline.started` with no terminal event; `manager.stopped` is what a reader keys on to retire it (the hooks write no liveness lockfile).
- **Liveness's primary signal is `manager.stopped` via SubagentStop.** When a `pipeline-manager` subagent ends, the SubagentStop hook emits `manager.stopped { run_id, agent_id }` (run_id resolved by the same session-keyed binding recovery as `tool.called`). A run with a `pipeline.started` and a `manager.stopped` but no terminal event is abandoned — **unless** a live `<run_id>.alive` lockfile still names a running driver (the Path-B supervisor poll-waiting on a nested blocker, which legitimately stops + re-spawns the manager). The **pid-lockfile machinery (`pipeline event write-liveness`/`clear-liveness`) is KEPT** — do NOT remove it: it is the only detector for a hard kill (SIGKILL / crash / power-loss never fire SubagentStop). `manager.stopped` is an event TYPE, not a schema-version bump. If you change the manager-stop contract, update `handleSubagentStop`/`hooks.json` (SubagentStop registration), `docs/events.md`, and `tests/hook-subagent-stop.test.ts` in lockstep. **The `SubagentStop` registration carries `"matcher": "pipeline-manager"`** — `SubagentStop` is one of the few events that supports a matcher (it filters on `agent_type`; `Stop` does NOT support one), and the value is a regex substring (the hyphen forces regex mode) that matches both the local `pipeline-manager` and the marketplace-namespaced `pipeline:pipeline-manager`, while excluding every other subagent (`step-executor`, `pipeline-improver`, …) so the hook stops spawning a Bun process for non-manager subagent stops. This narrowing is a pure perf optimization: the danger is UNDER-firing (which would drop the primary liveness signal), so the matcher must never be tightened in a way that fails to match the manager in either install form — and `handleSubagentStop`'s `MANAGER_SUBAGENT_RE` filter stays as defense-in-depth even though the matcher now pre-filters.
  **Nothing sweeps these locally today.** The dashboard daemon ran the sweeps and it is deleted; see `docs/events.md` § Dead-run signals. The signals are still emitted, which is what keeps reinstating a sweeper cheap.
- **The analytics/SessionStart hooks gate by WALKING UP from `cwd`, not by checking one directory.** `analytics-relay.ts` and `session-relay.ts` both call `resolveProjectRoot(cwd)` FIRST (which maps a git worktree to its MAIN repo + records the worktree tag), then gate with `hasPipelineDirUpTo(cwd, project_root)` — true if a `.pipeline` dir exists at `cwd` or any ancestor up to (and including) the project root. This is load-bearing and depth/worktree-independent: a terminal session is still inside the project whether it sits at the root, has `cd`'d into `.pipeline/<name>/steps/…` (hand-orchestrating a pipeline), or is inside a git worktree checked out under `.claude/worktrees/<name>/` (Claude Code spawns subagents there). Gating on a single `cwd/.pipeline` — or even `project_root/.pipeline` — silently drops every event in the nested cases. The walk is BOUNDED at the resolved project root so a stray `.pipeline` far up the tree (e.g. `$HOME`) can't misclassify unrelated projects. `hasPipelineDirUpTo` is duplicated byte-for-byte in both hooks (they can't import a sibling at runtime) — keep them in sync, and never revert the gate to a single-directory `existsSync` check. Event routing stays on `resolveProjectRoot`'s git root, so a worktree's events still land in the main repo's `.runtime`, tagged with `worktree`.
- **The journal/analytics hooks are ON BY DEFAULT — `PIPELINE_JOURNAL_ENABLED` is the master opt-OUT switch.** Every hook runs at entry UNLESS `PIPELINE_JOURNAL_ENABLED` is explicitly set to a falsy value (`0`/`false`/`no`/`off` disables; unset/empty — and any other value — enables). The gate is checked as the FIRST statement of `main()` in both `analytics-relay.ts` and `session-relay.ts` (before `process.cwd()`, the project-root walk, or any stdin read). When opted out: no events, no mirror bindings, no `session.opened`. The Bun process for a registered hook STILL launches (the registration lives in `hooks.json`; an env var cannot un-register it) but exits immediately — so the cost per hook call drops to ~Bun-startup only; to eliminate the spawn entirely the user must disable the plugin. The `journalEnabled()` helper exists in three independent copies (hooks can't import a sibling at runtime): `analytics-relay.ts`, `session-relay.ts`, and the CLI's, which lives in `apps/pipeline-cli/src/lib/event.ts` and is what `pipeline drive`'s session-binding writer (ux-v2 b7) goes through. Keep the three in sync, including the "only an explicit falsy value disables" semantics. The gate does NOT cover `pipeline event` (the journal writer is cheap and is what `pipeline logs` reads, so `/pipeline:run`'s lifecycle events are journaled even when the hooks are opted out). If you add a new hook entry point, add the same first-line enable check. **Opt out per-project** via `.claude/settings.json` `env`, or in the shell before launching Claude Code (hooks inherit the session environment). **Renamed from `PIPELINE_UI_ENABLED` in plugin-thin `p4`** (clean break, no alias) — that name was a leftover from the deleted local dashboard; the variable has always gated the JOURNAL, never a UI, and now says so.
- **`PIPELINE_JOURNAL_TRANSCRIPTS` is a SEPARATE, narrower opt-out that gates ONLY the transcript work.** ON BY DEFAULT (same falsy parse as `PIPELINE_JOURNAL_ENABLED`), it disables just the privacy-sensitive part: (a) the `transcript_path` pointer recorded on a mirror binding, and (b) the `Stop` hook's `turn.usage` transcript token tail — while leaving `session.opened` and the basic lifecycle events (`pipeline.*` / `iteration.*` / `tool.called` / `manager.stopped`) fully working. The gate lives at two seams, each of which independently prevents a transcript from being reached: the **binding writers** (`analytics-relay.ts appendMirrorBinding` + `pipeline event register-mirror-binding` in `event.ts`) still write the binding for run-correlation but with `transcript_path: null` when off; the **Stop hook** early-returns before tailing. The reader is duplicated in the two standalone packages that cannot import each other at runtime — `<cli>/src/hooks/analytics-relay.ts` and `apps/pipeline-cli/src/lib/event.ts` — keep the two in sync. **Orthogonal to** `PIPELINE_JOURNAL_ENABLED` (master) and `PIPELINE_STATS_ENABLED` (the `.stats` fold, gated in `stats-relay.ts` — this switch does NOT touch it). Regression coverage: `<superrepo>/tests/cross-repo/transcript-opt-out.test.ts` (reader parse + hook split + master-off subprocess) and the `register-mirror-binding pointer gate` block in `apps/pipeline-cli/tests/event.test.ts`.
- **Binding scope discipline (issue #11).** A session appears in `active-mirror-bindings.jsonl` only because a hook explicitly bound it — never by scanning `~/.claude/projects/`. A terminal Claude session that never spawns a `pipeline-manager` or worker must NEVER be named there, which is what keeps its transcript unreachable. `tests/mirror-scope-discipline.test.ts` is the load-bearing regression test for this invariant; do not weaken it. (The dashboard's `MirrorService` was the first consumer of the guarantee; `analytics-relay.ts`'s own `findBindingForSession` is the one that remains, and it is what makes an event's `run_id`/`step_uuid` resolvable at all — so the invariant is exactly as load-bearing as before.)
- **Event schema is versioned.** Every event carries a `schema` stamp. If you change the shape, bump the version AND keep readers backward-compatible for one version (so a reader at vN parses vN-1 events when the user upgrades the plugin mid-run).
- **Hook-side run_id correlation has four sources, in order: explicit override → `PIPELINE_RUN_ID` env → `session_id` lookup in `~/.claude/pipeline-ui/active-mirror-bindings.jsonl` → null.** The env var is the historical mechanism but is NOT propagated for Paths B/C — `/pipeline:run` exports it in a Bash subshell that never reaches Claude Code's parent process, and a terminal Path-C session never exports it at all. The session-keyed mirror-binding lookup is the load-bearing recovery: `/pipeline:run` (via `pipeline event register-mirror-binding`), the bypass-spawn PreToolUse handler, and — since ux-v2 b7 — `pipeline drive` all write bindings keyed by session_id, so the Stop and PostToolUse hooks can recover the run_id from there. Without it, every `tool.called` and `turn.usage` event during an actively-running pipeline stamps `run_id=null`. If you ever add a new event source that needs run-correlation, call `resolveBindingFromEnvOrSession(sessionId, projectRoot)` (or its run-id-only wrapper `resolveRunIdFromEnvOrSession`) from `<cli>/src/hooks/analytics-relay.ts` instead of reading `PIPELINE_RUN_ID` directly. Treats `PIPELINE_RUN_ID=""` as unset to prevent `run_id: ""` from leaking into the journal.
- **The DRIVEN path binds by construction: drive PRE-WRITES the session→(run, step) record before it spawns the child (ux-v2 b7).** `pipeline drive` pins each headless spawn's session id itself (`claude --session-id <uuid>`, `--resume` on an answer delivery), and Claude Code hands that same value to every hook firing **inside** the child. Drive therefore appends a `kind: "drive-session"` binding carrying the run UUID **and** the step UUID (ux-v2 b4) — `registerDriveSessionBinding` in `apps/pipeline-cli/src/lib/event.ts`, called from `drive.ts`'s `bindSession` — and `resolveBindingFromEnvOrSession` returns both. **The write must precede the spawn**; the child's first hook can fire milliseconds after exec, and a binding that lands afterwards misses exactly the events it exists to attribute. Measured end-to-end on a live `pipeline drive --json` (real `claude`, plugin hooks active in the child): **before, 10/10 hook events across two runs stamped `run_id: null`; after, 0/11, with every one of them also naming the step**. The one remaining `run_id: null` per run is `session.opened`, which `<cli>/src/hooks/session-relay.ts` writes as a **literal** `run_id: null` — a different hook that never consults the resolver, not a correlation failure. Binding lifecycle: no `terminal` record is written and none is needed — the run's own `pipeline.completed`/`halted` retires every binding sharing its `run_id` (`collectTerminatedRunIds`), and stale ones age out at `BINDING_MAX_AGE_MS`; a record whose spawn never happened names a session id that will never exist, so nothing can ever match it. Gated by `PIPELINE_JOURNAL_ENABLED` (the master switch promises "no mirror bindings" when off). **Shelf life is deliberate:** this whole mechanism depends on plugin hooks firing inside `claude -p`. When `-p` defaults to `--bare` they stop and it has nothing to attach to — a near-term improvement, not an architecture; the identity minting it propagates is the half that survives.
- **Binding terminal-state derives from TWO sources.** `findRunIdForSession` treats a binding as terminated when either (a) an explicit `terminal` record exists for that run_id in `active-mirror-bindings.jsonl` (Path-C bypass spawns write one), OR (b) a `pipeline.completed` / `pipeline.halted` event exists for that run_id in the project's `events.jsonl`. The second source is load-bearing because chain-controller bindings (Path B) never receive a `terminal` record — `pipeline event register-mirror-binding` has no counterpart subcommand. Without the events-jsonl check, every subsequent unrelated tool call in the same terminal session after a chain completes would re-attribute to the dead run forever. Bindings older than `BINDING_MAX_AGE_MS` (7 days) are also ignored as stale. On Windows the project_root filter compares paths case-insensitively to tolerate PowerShell-vs-Node drive-letter casing drift; on POSIX it's a strict compare. If you change the lifecycle event names or add a new "pipeline finished" event type, update `collectTerminatedRunIds` in lockstep.
- **The hooks never block Claude Code.** They always exit 0. The journal is the source of truth; every consumer of it is downstream and optional.
- **Per-run analytics are folded from the TRANSCRIPTS, not the hook events.** The hook-emitted `tool.called`/`turn.usage` are an unreliable stats source: ground-truth validation showed `turn.usage` (Stop hook, MAIN-transcript tail) never sees subagent tokens (per-run tokens came out ~0) and `tool.called` leaks ~half its events to `run_id=null`. The transcript fold reproduces ground truth exactly. The live implementation is `apps/pipeline-cli/src/lib/step-transcripts.ts` over **`apps/pipeline-cli/src/lib/vendor/transcript-walk.ts`** — a vendored copy kept because `apps/pipeline-cli` ships standalone to npm; see that file's header for the lockstep note. `pipeline logs --chat` reads the same transcripts for the terminal post-mortem view.

## Editing rules

- [`docs/events.md`](events.md) is the schema contract. Any change to event shape requires lockstep edits in: `apps/pipeline-cli/src/lib/event.ts`, `<cli>/src/hooks/analytics-relay.ts`, `<cli>/src/hooks/session-relay.ts`, `apps/pipeline-cli/src/commands/logs.ts` (the terminal renderer), `apps/pipeline-cli/src/lib/telemetry-outbox.ts` (the uploader's reader), and the relevant `/pipeline:run` emission line in `skills/run/SKILL.md`.
- **Bun is a hard requirement for the hooks.** The event journal is plain JSONL, so it can still be tailed from a shell without it.
- **Per-iteration token discipline still applies.** The hooks are side observers; they must never cause the main session or any subagent to read iteration content that they wouldn't have read otherwise.
