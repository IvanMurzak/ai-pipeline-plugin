- **`pipeline init` is the ONE-COMMAND entry point, and it is CLOUD-FIRST (owner decision, 2026-07-31 — supersedes task a1's local-first default).** `pipeline init [<template>] [--local] [--server <url>] [--org <slug>] [--project <slug>] [--no-runner] [--no-plugin] [--no-run] [--run] [--yes|-y] [--dir <path>] [--json]` (`src/commands/init.ts`, default template `support-answer`) runs, each step independently skippable and idempotent (a re-run prints `✓` per already-satisfied step): **(0)** checks `bun` (hard precondition — fails with the install URL, exit 1, nothing else runs); **(0.5) the cloud — FIRST, and by default**: composes `runCloud(['connect', …])` in-process (never a second auth ladder — one browser flow, one device flow, one machine-credential exchange in this package), passing `--server`/`--org`/`--project` through and answering the runner question `--runner` (a machine that is not a runner cannot pick up dispatched work). It is placed FIRST because the browser consent is the one step needing a human, and making it wait behind a plugin install is how a user walks away mid-setup. **A failure here WARNS and continues, exit 0** — everything below works unconnected, and an init that aborted on a declined consent screen would leave the user with nothing. `--local` skips it entirely (silently, like `--no-run`); combining `--local` with any cloud flag is a usage error rather than a silent win for one of them. **`--json` NEVER opens a browser** (`cloudStepDecision`): with `PIPELINE_MACHINE_TOKEN` it connects silently through the machine rung, without one it skips the cloud with a stated reason and still exits 0 — a browser flow under `--json` would block until its five-minute timeout and then fail. The real `cloudConnect` dep SWALLOWS connect's stdout under `--json`, because connect prints its own result object there and `init --json` owns the one-JSON-document contract (connect's progress already goes to stderr, and a failure still arrives as a non-zero exit code); **(1)** checks `claude` on `PATH`; **(2)** shells out to `claude plugin marketplace add IvanMurzak/ai-pipeline-plugin` + `claude plugin install pipeline@ai-pipeline` (both idempotent; a non-zero exit warns with its stderr and continues — the clone is still useful); **(3)** clones the starter pipeline by calling the SAME copy-tree primitive `pipeline clone` itself calls (`lib/templates.ts`) — an existing target reads as `✓ (already present)`, never clone's own exit-1 "refuse to overwrite" error; **(4)** offers to run the starter pipeline (interactive `[Y/n]`, default yes) by driving `commands/drive.ts`'s `runDrive()` **in-process**, reformatting the `step.started`/`step.completed`/`step.failed` progress events it already emits on `--json` into a compact per-step line with elapsed time — `init` does not reimplement any part of run orchestration; **(5)** prints exactly ONE next-action line (open Claude Code and `/pipeline:design`, or `Restart Claude Code to load the plugin.` when a session looks already open — a best-effort heuristic over `CLAUDECODE`/`CLAUDE_SESSION_ID`/`CLAUDE_PLUGIN_ROOT`, since no first-party session-liveness signal exists to check; or the missing-`claude` remediation; or `Next: pipeline run <template>` when the run didn't happen). **A missing `claude` skips BOTH the plugin install and the run and exits 0** (a precondition, not a failure) — the clone still runs. **`--json` is non-interactive and DECLINES the optional run unless `--run` is also given** (the opposite of the naive reading — the product-wide `--json` rule), emitting `{ok, cloud, plugin, template, path, ran, runOk?, warnings?}` with no prompt ever printed — `cloud` is `'connected' | 'skipped' | 'failed'` so a script reads THAT rather than grepping `warnings`. Exit `0` success · `1` a step failed (bun missing, or the starter run failed — reports the failing step + its output, since hiding a broken environment costs the user their next hour) · `2` usage. Full contract: `.claude/design/simplified-onboarding/03-pipeline-init.md` in the parent repo (immutable design doc — kept as originally shipped; describes a fourth "start the dashboard" step this file no longer reflects, see below). **plugin-thin `01-remove-local-ui.md` phase 1 (2026-08-02):** `init` no longer starts the local dashboard or mentions it — `--no-ui` is gone, and the checklist/JSON `ui` field are gone with it. `pipeline ui` itself is untouched and still works when invoked directly; this is advertising removal only, per that design's phasing table.

- **`pipeline clone <name>` scaffolds a bundled ready-made pipeline into a project — the local-first onboarding entry point.** `pipeline clone <name> [--force] [--dir <path>] [--list] [--json]` (`src/commands/clone.ts` + the `src/lib/templates.ts` registry) copies a bundled template's whole folder tree into `<cwd-or---dir>/.claude/pipeline/<name>/`. Templates SHIP INSIDE the package (`apps/pipeline-cli/templates/<name>/…`, a valid `PIPELINE.md` + `steps/` per template) and are resolved relative to the CLI's OWN source (`import.meta.dir`), never the cwd — so `clone` works identically from a plugin checkout and from an installed npm tarball (the published `bin` is `src/cli.ts` verbatim; `src/lib` → `../../templates` in both layouts). Cross-platform (`node`/`bun` `path`+`fs` only; `cpSync` recursive tree copy). It REFUSES to overwrite an existing `./.claude/pipeline/<name>/` unless `--force` (which removes-then-copies, so no stale file survives); `--list` prints the registry; an unknown name errors (exit 2) listing the available templates. Exit `0` cloned/listed · `1` target exists without `--force`, or copy failed · `2` usage. **Adding a template** (e.g. the real `support-answer` pipeline) = drop `templates/<name>/` (mirror `example-minimal`) + add a `{name, description}` entry to `TEMPLATES` in `src/lib/templates.ts`; that `.ts` edit trips CI, which runs `tests/clone.test.ts` — every registered template must plan cleanly (`computePlan` errors empty) — and `tests/packed-artifact.test.ts`, which asserts the template ships in the tarball. Contract is load-bearing across `src/commands/clone.ts`, `src/lib/templates.ts`, `tests/clone.test.ts`, and this section — change them in lockstep.

- **`pipeline department new`/`validate` author and check a `department.yml` — the ONE required file of a department project folder (simplified-onboarding design, task a8; builds on task a7's `lib/department-manifest.ts`).** `pipeline department new [<name>] [--engine <id>] [--from-pipeline <name>] [--force] [--json]` (`src/commands/department.ts`) writes `./department.yml` by default (D4) or `./<name>/department.yml` with a positional argument, and creates **that file and nothing else** — no `.claude/`, README, or starter agent (D3, a hard requirement). The scaffold's SHAPE is 05 §2's "Minimum viable file" verbatim (`apiVersion`, `name`, `description`, one `skills` entry, `runtime.engine`) — the design states outright *"This is what `pipeline department new` writes"* — with `name` slug-prefilled from the target folder and TODO placeholders elsewhere (sized above the 20-character "thin description" advisory so a fresh scaffold doesn't also nag about itself). `--engine <id>` picks the runtime engine (default `claude-code`; validated against the SAME registry `validate` checks against — `lib/department-manifest.ts`'s `ENGINES`). `--from-pipeline <name>` reads an EXISTING `./.claude/pipeline/<name>/PIPELINE.md` (this repo's own "pipelines live in the consumer project" path, not the bundled `templates/` `pipeline clone` copies from) via `lib/match.ts`'s `parseManifest`/`findFirstIteration` — the SAME `End State`/`Scope.In` parser the BM25 matcher is built on — and writes the department `description` from `End State`, the one skill's `description` from `Scope.In` (falling back to `End State` when `Scope.In` is empty, which is the case for all three BUNDLED templates today — their `## Scope` writes a plain `In:`/`Out:` line, and `lib/match.ts`'s `SCOPE_MARKER_RE` requires a leading `-`/`*`; a pre-existing gap in that module, not introduced or fixed here), plus `runtime.engine: pipeline` with `pipelineRoot`/`startIteration` resolved as POSIX-relative paths from the department.yml being written — a two-field runtime spec, so an existing pipeline becomes a department with NO editing (asserted by `tests/department.test.ts` re-`validate`-ing the written file with zero errors). Conflicts (a different explicit `--engine` alongside `--from-pipeline`) are a usage error. Refuses to overwrite an existing `department.yml`, or (a DISTINCT refusal, `<name>`-form only — the bare `new` never checks folder contents beyond `department.yml` itself, since the current folder is normally an existing project) to write into an already-occupied `<name>` folder, without `--force`, which covers both uniformly. Exit `0` created · `1` refused (exists / occupied / `--from-pipeline` pipeline not found) · `2` usage. `pipeline department validate [--file <path>] [--json]` (default file `./department.yml`) runs 05 §4's five check classes: **Schema + Version** come straight from `parseDepartmentManifest`'s own findings (task a7 — never re-derived here); **Coherence** flags a `communication` capability the manifest resolves to `true` that the named engine's DECLARED capabilities (06 §3) say it cannot honour (department-mesh `06-department-registry.md` §3.1's `acceptsMidTaskInput: true` + `adapter: pipeline-drive` example, generalized over all four booleans; engines with runtime-negotiated capabilities — `process`/`container` — are skipped, nothing to check against) and `contextAffinity: required` without a `per-context`/`daemon` `runtime.lifecycle`; **Engine** reuses a7's own "engine recognized, names every supported one" finding; **Advisory** covers a skill missing a `description` (an ERROR here, not the warning 05 §4's own prose table would suggest — BOTH 05 §4 and 02 §4 embed the identical worked transcript rendering it `✗` and counted into "1 error, 1 warning", and 02's preamble states outright that a transcript wins over prose on conflict — this module follows that rule explicitly, see `department.ts`'s header comment), a skill description under 20 characters (WARNING — the table's other example, undisputed), duplicate skill ids (already a warning from a7's own parser), `visibility` left unset (WARNING, matching BOTH transcripts' `⚠ visibility  not set` line even though it is not in 05 §4's own check-class table — detected via a raw one-key re-parse through the SAME `bunYamlParser` seam, not a second schema implementation), and `.claude/` present-but-empty (never a warning when simply absent); **Local** checks `engine: pipeline` actually pointing at a real pipeline (`pipelineRoot` exists, has a `PIPELINE.md`, `startIteration` exists inside it) and any other local `runtime` path (e.g. `workingDirectory`) existing on disk, resolved relative to the manifest's own directory. Findings are `{severity: "error"|"warning", field, message}` (task a7's own `ManifestFinding` shape); warnings NEVER affect the exit code. `--json` prints `{file, valid, errors, warnings, findings, notChecked}` — a stable, minimal shape shared by the clean-parse, errors-present, and file-missing/unparseable paths alike. **x51 put the required `runtime:` fields on the SAME table `serve` binds from.** A `pipeline`-engine manifest with no `runtime.startIteration` used to validate clean ("0 errors") and then be refused by `serve`, which cannot invoke `pipeline drive` without `--start` — the validate-says-yes/serve-says-no split x32 closed for the ENGINE field, in a second field. Each `ENGINES` row now declares its `requiredRuntimeFields` (`{field, why, severity}`), one predicate reads them (`missingRequiredRuntimeFields()`), and BOTH commands consume it: `validate` renders a finding at the declared severity with the declared sentence, `runtimeBindingFor` refuses with the SAME sentence whatever the severity. A field added to an engine is therefore checked by both commands or by neither. The ONE deliberate disagreement survives, but is now DECLARED rather than accidental: `runtime.command` on `process`/`container` is a **warning** at validate (because `department new --engine process` scaffolds without one — there is no honest placeholder for another project's binary) and still a hard refusal at `serve`. And because a clean validate still cannot promise a successful `serve`, the report ends with what it structurally could not check — that `pipeline-runner` is installed here and can start this engine, that the control plane accepts the registration (sign-in, org, plan limits, approval), and that the paths named exist on the OTHER machines serving this department — carried in `--json` as `notChecked`. Exit `0` clean · `1` errors present · `2` file missing or unparseable (05 §4's own two-vs-one-exit-code split — a null-manifest parse from a7 is ALWAYS exit 2, even if it happens to carry findings). `tests/department.test.ts` reproduces 05 §4/02 §4's own worked transcript byte-for-byte on the error/warning COUNT ("1 error, 1 warning" -> fix the stated skill description -> "0 errors, 1 warning", exit 1 -> 0) as its own Definition-of-Done proof. - **`pipeline department serve` takes an authored `department.yml` live in nine steps — the one command from a folder to a callable department (simplified-onboarding design, task a9; builds on a7's manifest/digest, a8's validate, a6's runner enrolment, and pipeline-runner's b1 `bind` verb).** `pipeline department serve [--org <slug>] [--runner-name <n>] [--detach|--foreground] [--json] [--file <path>] [--server <url>] [--device] [--reauth] [--machine-token <t>] [--runtime-command <cmd>]` (`src/commands/department.ts` for the order + the transcript, `src/lib/department-serve.ts` for every step that leaves the process) runs 05 §5's nine steps: **(1) validate in full** — the SAME composition `pipeline department validate` renders (`inspectManifestFile`, one function, two callers), any error aborting before anything is registered; **(2) authenticate** through the SAME 04 §4 ladder `cloud connect` uses (`commands/cloud.ts`'s exported `authenticateApi` — browser + PKCE, device-code fallback, `PIPELINE_MACHINE_TOKEN`/`--machine-token` client-credentials, D12), injected as `ServeCommandDeps.authenticate` so `lib/` never depends on `commands/` and `new`/`validate` never load the OAuth machinery; **(3) compute the digest** via a7's `buildRegistrationRequest` (never authored, never a placeholder — D15); **(4) register or update** — `GET /api/v1/departments` matched on SLUG (not a remembered id: that is what makes `serve` resumable from any partial state, keeps the department folder file-free, and lets a second machine serve the same department), then `POST` when absent, `PATCH` when the digest changed, a no-op when equal; **(5) enrol this machine as a runner** if `pipeline-runner status` reports no `runner_id`, by SHELLING OUT to `pipeline-runner register` through `lib/runner-enrol.ts` (D26 — never writing another package's config store; the OAuth client secret rides in `PIPELINE_RUNNER_OAUTH_CLIENT_SECRET`, never argv) with `installService: false` so step 7 keeps the one-service-per-machine decision; **(6) bind the runtime locally** by shelling `pipeline-runner bind --department <id> --adapter <adapterId> --command <cmd> [--arg …] --cwd <dir> [--lifecycle <l>] [--spec <json>]` — b1's verb, added precisely so this package can obey 05 §5 step 5's "never writes another package's config store directly" rule while still writing a store that lives in `pipeline-runner`'s config dir; `bind` signals a RUNNING supervisor to reload, which is why a machine that already has one can be live immediately rather than needing "restart the supervisor" — note *running*, which step 9 now verifies rather than assumes (x13); **(7) ensure the supervisor** — `readRunnerServiceState()` (a6's single machine-level check, shelled exactly once per invocation; `isRunnerServiceInstalled()` is now the `!== 'not-installed'` derivation of it) decides install-vs-nothing, so a machine that already runs one gets a binding, not a rival service (D26) — and its FULL state is carried into step 9, because `stopped` also means "installed" and x13 is precisely what happens when those two are conflated; the one time the state is re-read is immediately after this step INSTALLED a service, since the answer from before the install describes a machine that no longer exists (and Windows' backend starts the service best-effort, so exit 0 is not evidence of a running process); **(8) claim the install** — `POST /api/v1/departments/:id/installs {runner_id, manifest_digest}` (member+, c9/D13); **(9) verify, then report.** `⏸ waiting for an admin to approve` + `https://<app>/departments/<slug>` when `install.pendingApproval` (07 §4 — read from `pendingApproval`, NOT `auto_approved`, which is false on an idempotent re-serve of a live department; exit 0). Otherwise the outcome is DERIVED from two observations, never from the fact that steps 1–8 succeeded (**x13** — `serve` used to print `● online` unconditionally, and did so in the `e2` gate on a machine whose supervisor service was `stopped (auto-start)` while the control plane reported `online: false`). The observations are (a) **this machine's supervisor SERVICE**, via `readRunnerServiceState()` — the full `running`/`stopped`/`not-installed`/`unknown` state, *not* `isRunnerServiceInstalled()`'s boolean, because a stopped service is installed; (b) **this machine's supervisor PROCESS** (**x39**), via `readLocalDaemonState()` over `pipeline-runner bind`'s OWN stdout — b1's `signalSupervisorReload()` reads `<home>/runner.lock` (the per-home exclusive lock every daemon takes at `start`, `core/home.ts`, 07 §2.2) and probes the recorded pid, so it reports `running`/`none` for a supervisor of ANY kind, foreground included, scoped to the runner HOME and therefore honouring `PIPELINE_RUNNER_HOME`; and (c) **the control plane's own `online`**, via `GET /api/v1/departments/:id`, which is the sole authority for the word (`mesh-registry/service.ts#isDepartmentOnline`: an `active` install whose runner holds a live gateway connection). The cloud decides whether `online` may be said; the local state decides what to say instead and what the user should do next — `online: false` names no cause, and the usual cause is knowable locally for the price of shells `serve` was already paying. **(a) and (b) are kept separate because neither subsumes the other, and that is exactly what x39 fixes**: `service status` is structurally blind to a foreground supervisor, to a daemon in an isolated `PIPELINE_RUNNER_HOME`, and to a service under another OS account, so x13's rule — "read the verdict off the service probe" — declared a live `--foreground` department `○ registered — not serving … another machine is serving it, but this one is not` and exited 1, about the very machine that was serving it (found by the P4 gate; x13 had replaced a false success with a false failure). Two rules follow, and they are the whole of `assessLiveness()`'s contract: **positive evidence wins over the absence of the other probe's** — a process demonstrably holding this runner home is a supervisor, service or not, and `localSupervisorIsUp()` is the ONE predicate the transcript, the confirm-backoff and the verdict all ask (so they cannot drift, the x32 lesson applied here) — and **a cause is stated only when it is established**: "it is being served from somewhere else (another machine, or another runner home on this one)" needs (b) to have ruled this home out, and without it the message says what IS known ("this check cannot tell whether that is this machine") rather than naming a machine it never looked at. The residual blind spot is named rather than papered over: a daemon in a DIFFERENT runner home (another OS account's service with its own `PIPELINE_RUNNER_HOME`) holds a lock file this cannot read — the same blind spot as **x22** — which is why the sentence says "another machine, **or another runner home on this one**" instead of picking one. `assessLiveness()` (`lib/department-serve.ts`, pure, exhaustively unit-tested) maps the evidence onto exactly three outcomes: **`● online, ready for work`** (exit 0) only when the control plane said `true`; **`○ registered — not serving (<reason>)`** plus a named remedy (exit 1) whenever something was positively observed that rules it out — a stopped supervisor (`Start it: pipeline-runner service start` — **x44/x24**: that verb now exists on all three backends and starts the already-installed service without re-registering it or needing an elevated shell; it used to say `service install`, which reached `running` by stop+delete+recreate, purely because no start verb was exposed. `not-installed` is a different state and still names `service install`; where the service probe said nothing at all both are named, since `service start` refuses — naming `install` — when there is nothing installed to start. ⚠ `service start` is on pipeline-runner's `main` and is **not in a published release yet** (npm's latest is 0.6.0), so on the runner most machines have installed it fails with `unknown service command 'start'` — loudly, per x11, which is right, but a loud failure with no next step is still a dead end. The hint therefore carries one: *"If that verb is unknown, this machine's runner predates it: `bun add -g @baizor/pipeline-runner`"*, phrased as a condition rather than a version so it needs no maintenance), no supervisor of EITHER kind / `--foreground` with nothing running (`pipeline-runner start`), or a running supervisor the control plane does not see; and **`◌ registered and bound; could not confirm it is live (<why>)`** (exit 0 — every step this command controls succeeded) when neither could be read. `cloudOnline` is `true | false | null` and `null` is never spelled `false`. When a supervisor IS running but the department is not yet online — the ordinary fresh-install race, since `service install` starts the process and its gateway connection lands a moment later — the read is retried on a short backoff (1s/2s/4s/8s, ~15s worst case, announced on the transcript) and never when there is nothing to wait for. Exit 1 for `registered — not serving` is deliberate and matches `--foreground`'s pre-existing contract: `serve` is the "make it live" command, so an exit 0 next to a department that is not taking work would be the same false success in a different channel; the "this is an incomplete outcome, not a broken one" nuance is carried by the message and by `--json`'s `state`/`liveness`. **Two invariants worth stating loudly.** First, the `runtime:` half never leaves the machine: the body is a7's allow-list projection, re-checked by `assertNoLocalFields` on the way out, so `command`/`args`/`workingDirectory`/`environment`/the engine name are structurally absent — asserted directly in `tests/department-serve.test.ts`. Second, **the cloud's `pipeline-drive` coherence check can no longer fire** (`mesh-registry/manifest.ts`'s `validateManifestCoherence` gates every rule on `runtime.adapter`, which is now never advertised), so the equivalent is enforced LOCALLY and EARLIER by `coherenceFindings` over a7's engine registry — the capability booleans plus `EngineDefinition.supportedLifecycles` (`pipeline` → `per-task` only, 07-runtime-contract §2.1). Anything added to the server's list must be mirrored in that registry or it is dead code. **Refusals before anything is registered:** an invalid manifest (exit 1, or 2 when missing/unparseable), a runtime this machine cannot bind (a missing `runtime.command` for `process`/`container`, a missing `runtime.startIteration` for `pipeline` — the runner's own store would silently drop the spec), and an engine the registry has no row for (registering a department that could not execute one task is worse than one honest refusal naming the engines that exist). **x32 removed a fourth refusal that had become a bug**: this module carried a second, hand-written engine list (`SERVABLE_ADAPTER_IDS`) that went stale the moment task `b3` shipped `ClaudeCodeAdapter`, so `serve` printed `✓ engine claude-code  (supported)` from the registry and then refused the same manifest one screen later with "no engine module for 'claude-code' ships in pipeline-runner yet" — leaving `claude-code`, `department new`'s own default and the engine the whole P4 phase builds, unreachable through the one command that takes a department live. There is now ONE engine list (`lib/department-manifest.ts`'s `ENGINES`) and one predicate (`isSupportedEngine()`) behind both messages, so they cannot disagree; `engine: claude-code` binds `--adapter claude-code --command claude --cwd <department folder>` with no nested spec (pipeline-runner's `ClaudeCodeAdapter` builds its own flag surface and appends `runtime.args` verbatim), and `--runtime-command` overrides the `claude` binary the same way it already overrode `pipeline` — a machine-local install path never belongs in a cloned `department.yml`. The remaining exposure is that `ENGINES` mirrors pipeline-runner's `ENGINE_REGISTRY` by hand with no dependency edge between the packages (tracked as **x14**, an open architecture decision, and deliberately still open — deleting the mirror is that task's call). `tests/department-serve.test.ts` carries a drift check that reads the runner's `engine.ts` when both repos are checked out side by side, but **x44** states plainly what it is worth: it is vacuous on this repo's CI (no `public/pipeline-runner` on disk) and vacuous for every user (no runner source tree at all — only an INSTALLED runner, whose registry is the only one that can actually break a department). So x44 moved the load to runtime instead: `pipeline-runner bind --adapter` now REFUSES an id it has no engine module for and names the ones it has, step 6 provokes that refusal against the installed build on every invocation, and `parseAdapterRefusal()`/`describeAdapterRegistryDrift()` turn it into a named version skew between the two packages — `engine: claude-code` maps to adapter `claude-code` here, the installed runner registers `<list>`, upgrade whichever is behind — rather than relaying an opaque complaint about an adapter id the user never typed. `bind` failing for any other reason (an unwritable store, a missing `--command`, a missing binary) keeps its own message, and a future rewording of the runner's refusal costs the richer message and falls back to the verbatim relay. **Every 05 §5 failure row has its stated message**: offline (`Could not reach … — nothing was registered. Your local pipelines are unaffected.`), slug taken, the c8 plan ceilings (the server's own D29-named 402 sentence relayed verbatim — never a bare 402), `Registered, but this machine could not be enrolled: <reason>`, `Could not write the runtime binding: <path> (<reason>)` (b1's own text), `Registered and bound, but the supervisor could not be installed: <reason>`, and `Registered, but the install could not be claimed: <reason>` — each exit 1, each leaving the department registered and inert rather than rolling cloud state back. **`serve` writes NOTHING inside the department folder** — no state file and deliberately no `.claude/pipeline/cloud.json`, which would pin a clonable repo to one org and one server; the credential lives in the per-user store (written by the shared ladder) and the binding in `pipeline-runner`'s config dir (written by `pipeline-runner bind`). `--json` emits one object (`{ok, state, org, department, runner, binding, supervisor, install, liveness, url, warnings, error?}`) on stdout with every progress line on stderr — `liveness` being x13's `{verdict: 'live'|'not-live'|'undetermined', supervisorState, localDaemon, cloudOnline, reason?, nextStep?, cloudError?}`, `null` when step 9 was never reached, and the reason a scripted caller never has to infer liveness from `ok` — `localDaemon` (`'running'|'none'|'unknown'`, x39) is the process probe reported NEXT TO the service one, so a script can tell `--foreground`'s `{supervisorState: 'not-installed', localDaemon: 'running'}` (a live machine) from `{supervisorState: 'not-installed', localDaemon: 'none'}` (an idle one), which is precisely the distinction whose absence produced a wrong verdict and an invented cause. Exit `0` online, awaiting approval, or unconfirmed · `1` a step failed (re-run to converge), or the department is registered and NOT serving · `2` usage, or a missing/unparseable manifest. - **`pipeline department status`/`stop`/`retire` are the operator's day-to-day surface after `serve` (simplified-onboarding design, task a10; builds on a9's `renderState` vocabulary, `runtimeBindingFor`, and pipeline-runner's b1 `bindings`/`unbind` verbs).** A department folder is a clonable git repo and stores none of its own state (a9's rule) — none of these three verbs writes a file inside it either, and all three resolve the department id (which lives only in the cloud and in `pipeline-runner`'s binding store) the SAME way: `resolveLocalDepartmentId`/`resolveDepartmentId` in `src/lib/department-serve.ts` re-derives, PURELY LOCALLY, the exact `RuntimeConfig` `serve` would bind for `department.yml` RIGHT NOW (`runtimeBindingFor`), shells `pipeline-runner bindings --json`, and matches on `cwd` — a department folder's own absolute path, which by construction cannot be shared by two different `department.yml` files, so `cwd` alone is already a unique local key (`adapterId`/`command` ride along as a sanity check; `args`/`lifecycle` are deliberately excluded so a hand-edited bind flag can't defeat the match). - **The `pipeline` CLI is where deterministic, LLM-free work lives.** `apps/pipeline-cli/` is a single local TypeScript app run with Bun (`bun "${CLAUDE_PLUGIN_ROOT}/apps/pipeline-cli/src/cli.ts" <command>`) — no build step for the plugin's own use, exactly like `apps/pipeline-ui/server.ts`. The principle: anything an agent would otherwise compute by reading files (enumerating steps, resolving models, building/validating a DAG, deciding what runs next) belongs here instead, so the agent reads ONE compact result and pays near-zero tokens. **Commands: `hash`, `plan`, `match`, `event`, `route`, `next`, `ui`, and `logs`.** `pipeline hash --root <pipeline_root> [--json]` computes the deterministic SHA-256 content hash of a pipeline — `PIPELINE.md` + every file under `steps/**` and `scripts/**` — and outputs `sha256:<hex>` (plain) or `{"content_hash":"sha256:<hex>"}` (`--json`). The hash is order-independent (files sorted by POSIX-relative path), rename-sensitive, and OS-stable (CRLF→LF normalized by default). This is the SAME identity the cloud registry uses (`registry/hash.ts`) and runners verify against lease pins; the runner (`c4` task) shells this same CLI to verify content hash before executing. Exit 0 on success / 2 on missing/invalid root. `pipeline plan --root <pipeline_root> [--default-model <m>] [--model <step_id>=<m> ...] [--default-effort <level>] [--effort <step_id>=<level> ...]` reads `PIPELINE.md` + every `steps/**/*.md` frontmatter and prints the execution plan JSON (`mode`, `isolation`, `default_model`, `default_effort`, ordered `steps` with effective `model` + `effort` + `depends_on`, DAG `layers`, normalized `model_overrides` + `effort_overrides`, `errors`, `warnings`; exit 1 when `errors` non-empty; repeatable `--model`/`--effort` pin single steps at HIGHEST precedence — beat the step's own frontmatter; `inherit` forces the session default; invalid value → warn + drop, unknown step_id → warn + keep for off-plan steps). **Reasoning effort (`effort:` frontmatter + the two flags) resolves through the exact same ladder as the model** — override ?? step ?? pipeline ?? null (inherit); vocabulary `low|medium|high|xhigh|max|inherit` (verified against `claude --effort`); `normalizeEffort` in `plan.ts` is the single validator — still public/library-exported, though the manager now reaches it transitively through `pipeline next`. `pipeline match --pipelines-dir <dir> (--task <t> | --issue <ref>) [--top N] [--neg-threshold N]` is the BM25 matcher both `/pipeline:find` and `/pipeline:dispatch` tier 1 call. `computePlan()` / `matchPipelines()` / `computeNext()` are library-exported (`src/index.ts`) for embedding in other local projects, and `bun run build` emits a Node-targeted `dist/cli.mjs`. The model-resolution rules in `plan.ts` MUST match the documented vocabulary (aliases `haiku|sonnet|opus|fable`, `claude-*` ids, `inherit`/absent→null) and the `MODEL_SHORTHAND_TO_ID` story in `lib.ts`; the mode gate (`execution: parallel` required, `depends-on` alone → warning) MUST match `pipeline-designer.md` + `pipeline-manager.md`. `pipeline event <type|write-liveness|clear-liveness|register-mirror-binding> [k=v…]` is the runtime UI-event emitter that `/pipeline:run` (supervisor lifecycle + liveness + mirror binding) and `pipeline-manager` (retrospective improver/script events ONLY — the main-loop per-iteration events are auto-emitted in-process by `pipeline next` via the same `emitEvent()` writer) call. `register-mirror-binding` honours `PIPELINE_UI_TRANSCRIPTS` (default ON): when off it still records the binding for run correlation but with `transcript_path: null`, so the daemon never mirrors that session's transcript — orthogonal to `PIPELINE_UI_ENABLED` and `PIPELINE_STATS_ENABLED` (see docs/ui-subsystem.md). **`pipeline route --root <pipeline_root> --run-id <id> --from <step_id> --flags <json>`** is the standalone Variant-A routing engine: for a pipeline that opts in with a `## Graph` JSON block in `PIPELINE.md` (a map of `step_id` → conditional edges `{when, goto|done, max}`), it evaluates graph + the just-finished step's result flags + this run's per-edge counters (persisted at `<pipeline_root>/.runtime/<run_id>/route.json`, gitignored) and prints the next action (`run`/`done`/`halt`). This is what makes bounded-retry loops (e.g. a `review` step looping back to `implement` up to `max: 3` times, then skipping) declarative — the counter/skip logic lives ONCE in the graph + `graph.ts`, never duplicated in step bodies. A pipeline with no `## Graph` section is untouched (legacy sequential/DAG via `next_iteration`). `computePlan()` surfaces + validates the graph (dangling/duplicate goto, bad `max` → plan errors). `pipeline route` stays public/library-exported, but inside a run the manager no longer calls it directly — `pipeline next` consumes `routeNext()` internally (see the mechanical-manager bullet). - **Pipeline variables (`${PP_*}`) parameterize a pipeline across runs — declared once, supplied per run.** An optional `## Variables` section in `PIPELINE.md` (authoring guidance: `pipeline-designer.md`) declares `- PP_NAME (required)` / `- PP_NAME (default: ...)` bullets; iteration/manifest BODY text and a script step's `command:`/`script:` values then reference one as `${PP_NAME}`, with an optional inline fallback — `${PP_NAME:-default}` (used when the variable is unset OR empty, POSIX `:-`) or `${PP_NAME-default}` (unset only; a resolved-empty value is kept) — and `$$` escapes a literal token (`$${PP_NAME}` renders `${PP_NAME}`, never expands). `next`, `drive`, and `step run` all accept the same repeatable `--var NAME=value` (split on the FIRST `=` only, so `PP_URL=a=b` resolves to `a=b`; `NAME=` is an explicit resolved-empty value, distinct from unresolved) and `--vars-file <path>` (dotenv format: `KEY=VALUE` lines, `#` comments, optional `export ` prefix; a malformed line is a loud startup error naming the line NUMBER, never silently skipped or partially applied) — `--vars-file` entries load first, a same-named `--var` flag wins. Each declared name resolves `--var`/`--vars-file` > the operator's environment > the manifest `(default: ...)` (a `required` variable is NEVER satisfied by a default — manifest or inline — only by a supplied value); resolution is validated FAIL-FAST and AGGREGATED (never first-error-only) before any run action: a missing required variable, an unknown supplied name (a typo, or a project `.env` pointed at by mistake — non-`PP_`/undeclared entries are rejected, never bulk-imported), or any other substitution problem halts listing every problem, each variable's declaration line, and every occurrence (file:line), plus the exact remedy. On `next`/`drive` the resolved map is FROZEN into `next.json` at run init: `--resume` reuses it VERBATIM (no environment re-read — environment drift mid-run can never change a running pipeline's values), and supplying `--var`/`--vars-file` against an already-frozen run is a loud usage error (exit 2, state untouched) — start a new run to change values. A run whose saved state PREDATES the `variables` key (an older run, or the pipeline's FIRST run after gaining declarations) accepts `--var` one more time and writes the resolved map back (one-time migration, never repeated). `step run` resolves identically but NEVER freezes or persists anything (ephemeral, dry-run only — see its own bullet below). **Trust rules**: `PP_*` values are non-secret configuration BY CONTRACT — they are visible verbatim in rendered files, params files, child-script environments, logs, events, and (for agent steps) the step-executor's LLM context, where a substituted value is **untrusted data, never an authored instruction** — never design a variable to carry a secret (secret-looking names are lint-warned; scripts keep reading real secrets straight from the process environment). **Footgun**: no registry reserves the `PP_` namespace, so a `PP_*` name already set in the operator's shell/CI environment silently satisfies a declared variable via the environment tier — no flag, no prompt; check your environment (or pass an explicit `--var`, which always wins) before running an unfamiliar pipeline. Script-step argv/env/Params substitution details — including the argv[0]-substitution ban and the `.bat`/`.cmd` block — live in `docs/script-steps.md`.

- **`pipeline next` is the orchestration state machine — the `pipeline-manager` is now a thin actuator over it.** `pipeline next --root <pipeline_root> --run-id <id> [--start <iteration-path>] [--default-model <m>] [--model <step_id>=<m> ...] [--default-effort <level>] [--effort <step_id>=<level> ...] [--record '<json>' | --record-file <path>] [--manual-scripts] [--resume]` (`apps/pipeline-cli/src/lib/next.ts` + `src/commands/next.ts`) owns ALL run control flow: sequential advancement off the step's `next_iteration`, graph routing (it consumes `routeNext()` + persists the same per-edge counters in its own `next.json`, so it does NOT call the `route` command), DAG-layer stepping, the Tier-1 improver / script-creator gating, the end-of-run retrospective gate (it counts `<pipeline_root>/.feedback/<run-id>/*.md` itself), and the terminal `done`/`halt`/`blocked` decision. Each call returns ONE action — `run-step` (with `concurrent` + a `steps` list of `{step_id,path,model,isolation,index}`; for an `external`-isolation run each step also carries `worktree_path` + `worktree_env_file` + `external_worktree:true` as informational context), `merge` (worktree branches), `run-improver`, `run-script-creator` (`number`/`of`), `retrospective`, `continue` (a `type: script` call-budget boundary — see the script-step paragraph below), `done`, `halt` (`reason`+`status`), or `blocked` — and the manager performs it, then calls again with `--record '<json>'` (or `--record-file <path>`, pointing at a JSON file — for step records, the file the step-executor wrote itself at `<pipeline_root>/.runtime/<run-id>/records/<step_id>.json`, eliminating manager transcription) describing the outcome (`{kind:"step"|"layer"|"merge"|"improver"|"script"|"retro"|"worktree"|"continue", …}`; the `worktree` record carries `phase:"provisioned"|"torn-down"`, and `{kind:"continue"}` is the caller's no-op reply to a `continue` action). The engine's `provision-worktree`/`teardown-worktree` actions (external isolation) are consumed INSIDE the command by default: `commands/next.ts` executes the consumer's create/destroy hook in-process (`lib/hooks.ts`), emits `worktree.created`/`worktree.destroyed`, feeds itself the worktree record, and returns the next REAL action with top-level `provisioned:{worktree_path,branch,env_file}` / `teardown:{ok,detail}` info attached (a create failure → terminal `halt` with reason `worktree-create hook failed: …`; a destroy failure never strands the run); the `--manual-hooks` flag restores the legacy raw provision/teardown actions for a caller that actuates them by hand. **`type: script` steps are executed IN-PROCESS the same way — zero LLM tokens** (the frozen process I/O contract lives in `docs/script-steps.md`): when a `run-step` action's `steps[]` includes a `type:"script"` member, `commands/next.ts` resolves its `## Params` bindings into `<pipeline_root>/.runtime/<run-id>/params/<step_id>.json`, spawns the script through the shared `HOOK_RUNNER` wrapper (interpreter resolved by extension via `lib/hooks.ts`), takes the last-JSON-object line of stdout as the result, persists `output` to `<pipeline_root>/.runtime/<run-id>/outputs/<step_id>.json`, writes an attempt-ledger entry keyed by `(step_id, dispatch_index)` (double-execution protection across kills/crashes), synthesizes the `{kind:"step",outcome:"completed",flags,output}` record itself, and returns the next REAL action — so script chains cost nothing and the caller never sees them. A failure writes a failure record (`.runtime/<run-id>/failures/<step_id>-<dispatch_index>-<attempt>.json` + a sibling `.log`) and a `.feedback/<run-id>/` file, then follows the step's `on-failure` policy — `halt` (default) or re-dispatch the SAME step as an agent-type `run-step` carrying `fallback:'script-failure'` + `failure_record` — while `retries:` re-runs class-`transient` failures mechanically and `env` always halts. Because in-process scripts run inside the manager's 10-minute Bash call, the command enforces a soft **call budget** (`CALL_BUDGET_MS`/`SAFETY_MARGIN_MS`/`MANAGER_SAFE_TIMEOUT_S` in `lib/script-types.ts`): a script that would not fit the remaining budget yields a **`continue` action** — the caller performs nothing and immediately re-calls `pipeline next … --record '{"kind":"continue"}'` in a fresh Bash window, so a chain of script steps spans any number of calls (`pipeline drive` runs with an infinite budget — only the per-call execution cap can still yield `continue`, which drive answers itself with the same record). Script members of a concurrent DAG layer run first and are held in `state.partial_layer_results`, so the returned `run-step` carries only the agent members. `--manual-scripts` (mirrors `--manual-hooks`) restores raw script-step `run-step` actions for a caller that executes + records them by hand. The script-step record/action contract is load-bearing across `lib/script-step.ts` + `lib/script-types.ts`, `next.ts`, `commands/next.ts`, `step-schema.ts`, and `docs/script-steps.md` — change them in lockstep. - **`pipeline step run` is the author's harness for a single `type: script` step — no run required.** `pipeline step run <iteration.md> [--param k=v …] [--json]` resolves the step's `## Params` (statics / `default`s; a `${steps.…}` binding REQUIRES a matching `--param` override — else exit `2` with a clear message, since there is no run to read a prior step's `output` from), executes the script exactly as the runtime would (same env / cwd / timeout machinery + the frozen `PIPELINE_STEP_*` env contract in `docs/script-steps.md`), and prints the parsed result + the would-be `{kind:"step",…}` record (`--json` for machine form). It **NEVER touches any run state** — no records, ledger, outputs store, or feedback. Exit codes: `0` the script ran and returned `ok:true`; `1` it ran but failed (`ok:false` or a failure class); `2` usage — bad args or an unresolved `${steps.…}` binding with no `--param`. This is how a pipeline author tests a script step in isolation; the full runtime path is `pipeline next` (script-step paragraph above). `--var NAME=value` / `--vars-file <path>` resolve the pipeline's declared `PP_*` variables (same precedence and fail-fast validation as a real run — full contract in the "Pipeline variables" bullet above) and substitute them into the step's `command:`/`script:` surfaces + `## Params` bindings exactly like a real run, but EPHEMERALLY: nothing is frozen, persisted, or written back — an unresolved required variable is a `2` usage error, same as an unresolved `${steps…}` binding. Contract shared with `lib/script-step.ts` / `lib/script-types.ts` + `docs/script-steps.md` — change in lockstep.

- **`pipeline submodule bump` is a GUARDED git primitive — the mistake is impossible by construction, not by care (Phase-1 of the guarded-CLI architecture).** `pipeline submodule bump --project-root <superproject> [--submodules a,b] [--base <branch>] [--source-worktree <path>] [--dry-run] [--json]` (`src/commands/submodule.ts` + `src/lib/{land,drift,git}.ts`) records superproject submodule-pointer change(s) on the base branch and pushes them **isolation-safely**: the shared checkout is NEVER `checkout`/`reset`/`switch`ed — its ONLY mutation is `fetch` + `merge --ff-only`; all branch/commit work happens in a THROWAWAY worktree off `origin/<base>`. It is the TS port of the consumer project's tested `_lib/land_to_main.py` + `_lib/submodule_drift.py` and embodies the guards whose ABSENCE caused this session's incidents: **fork-diff safety** (a pointer that differs only because base advanced past the run's fork is NOT bumped/reverted — the #132-revert fix, applied to pointers), **conflict** (a pointer base changed since the fork is skipped + surfaced, never clobbered), **reachability** (only bump to a commit reachable from the submodule's `origin/<default>` and strictly ahead of the recorded pointer), **pre-flight self-clean** (orphaned `land-*` throwaway worktrees + stale scratch branches from prior KILLED runs are reaped BEFORE anything is created, so correctness never depends on a `finally` — idempotent under a mid-run SIGKILL), and **STOP-on-error** (halt with a structured `halt_reason` + the exact manual recovery; the post-merge reconcile retries the transient index.lock/propagation-lag race with bounded backoff, then halts — never forces). Everything is expressed over injectable `GitRunner`/`GhRunner` seams (`src/lib/git.ts`) so `tests/submodule-*.test.ts` (sharded; shared world in `tests/_submodule-world.ts`) proves each guard against REAL git sandboxes (a local bare origin + a fake-gh that ff-advances it) — the isolation invariant is asserted from the git call log. `landToMain`/`classifyDrift`/`bump` are library-exported from `src/index.ts`. **A finalize hook wires it as** (paths absolute): `bun "${CLAUDE_PLUGIN_ROOT}/apps/pipeline-cli/src/cli.ts" submodule bump --project-root "$PIPELINE_WT_PROJECT_ROOT" --source-worktree "$PIPELINE_WT_WORKTREE_PATH" --base "$PIPELINE_WT_BASE_BRANCH" --json` — but the consumer finalize-hook wiring is NOT yet done (the TD does that after review). The guard-behavior contract is load-bearing across `land.ts`/`drift.ts`/`git.ts` + `tests/submodule-*.test.ts` (sharded; shared world in `tests/_submodule-world.ts`) + this README's `submodule bump` section — change them in lockstep; each guard has a named test that replays its incident.

- **`pipeline drive` is the EXPERIMENTAL headless runner — an entire pipeline run with NO pipeline-manager LLM agent.** `pipeline drive --root <pipeline_root> --run-id <id> --start <iteration-path> [--default-model <m>] [--model <step_id>=<m> ...] [--default-effort <level>] [--effort <step_id>=<level> ...] [--resume] [--answer <text> | --answer-file <path>] [--task <text> | --task-file <path>] [--executor-cmd <template>] [--json]` (`src/commands/drive.ts`) is the opt-in counterpart to the manager (selected per pipeline via `runner: headless` frontmatter; the command itself takes explicit args and never reads that field). `--var NAME=value` / `--vars-file <path>` forward to the same engine init `next` uses — resolved once, FROZEN into `next.json`, and a frozen resume rejects new values with a usage error (exit 2) — full contract in the "Pipeline variables" bullet above. It loops over the SAME engine invocation `pipeline next` uses — the exported `invokeNext()` in `commands/next.ts`, so `next.json` persistence, no-record auto-resume, in-process worktree-hook execution (external isolation, incl. finalize), and per-iteration UI-event auto-emission are byte-identical — and actuates each action itself: **`run-step`** performs the manager's run-start setup once (`.feedback/<run-id>/` + the `.feedback/.gitignore` `*` stub + `.runtime/<run-id>/records/` + `.runtime/<run-id>/sessions/`), builds the EXACT manager-documented step-executor spawn prompt (`run_id` / `pipeline_root` / `step_record_file` lines + the protocol paragraphs; removed at done/halt) — and the record is taken from, in order: **(1)** the envelope's schema-validated `structured_output` (`lib/envelope.ts` parses it, `lib/step-schema.ts` is the single-source schema — authoritative wherever `--json-schema` still works, e.g. <= 2.1.205), **(2)** the DROP record file, **(3)** the legacy canonical `.runtime/<run-id>/records/` file (custom templates / older parked sessions whose earlier prompt named it), **(4)** the final-response TEXT parsed as a JSON object (`lib/envelope.ts parseResultObject` — whole text, fenced block, or prose-wrapped span; the headless prompt demands the exact record object as the final response). Whichever channel wins, drive persists the canonical `.runtime/<run-id>/records/<step_id>.json` observability copy ITSELF (drive's own fs write is never permission-gated; every consumer-facing record path — blocker briefs, final JSONs — is the canonical copy). Envelope `usage`/`total_cost_usd` accumulate into `.runtime/<run-id>/usage.json` and enrich the run's `.stats/` tokens (incl. `cost_usd`) at the terminal action — headless runs have no manager transcript for the stats hook to fold; the same terminal enrichment (done/halt only — blocked/awaiting parks skip the walk; the whole fold is skipped when stats are disabled) also folds each pinned step session's transcript — current AND `previous_session_ids` loop-back executions (`lib/step-transcripts.ts`) — for `tools_called`/`tools_failed`/`agents_spawned` + per-failure detail lines with EXACT step attribution, and uses the transcript-folded token totals as the FALLBACK token source when no envelope usage accumulated (custom template without `--output-format json`, or every attempt crashed pre-envelope); all-zero from both sources leaves the record `pending` — never measured-as-zero. Concurrent layers spawn all steps in parallel (`Promise.all` over the seam) and fold their records into the `{"kind":"layer"}` record (`worktree_branch`/`worktree_path` from each record when present, else null). **Sessions — every spawn is pinned + resumable**: drive generates a UUID per step attempt, persists `.runtime/<run-id>/sessions/<step_id>.json` (`session_id`, `status: running|awaiting-input|done`, `spawn_cwd`, `previous_session_ids[]` — ids replaced by a same-run re-execution (graph loop-back), kept so the terminal stats fold covers every execution — `questions[]`, `crashes`; shape + reader single-sourced in `lib/step-transcripts.ts`, drive is the writer) BEFORE the spawn, and passes `--session-id <uuid>`. Re-entry while parked WITHOUT `--answer` re-surfaces the stored question and spawns nothing. At most `MAX_QUESTIONS_PER_STEP` (3) questions per step, then halt; needs-input inside a PARALLEL layer maps to halted (v1 — parallel steps must be self-contained). **Crash-resume**: an attempt ending with NO valid record — or a session file left `running` by a died drive process — is resumed via `--resume <session-id>` with an "interrupted, verify and continue" prompt, up to `MAX_CRASH_RESUMES` (2) per session, then the halted synthesis above. **Per-step permission mode**: `permission-mode:` frontmatter (step ▸ manifest ▸ `acceptEdits`; - **`pipeline gc` is the leak janitor — verify (and, with `--clean`, reap) worktrees/branches left behind by crashed or killed runs.** `pipeline gc [--project <path>] [--clean] [--json] [--no-submodules] [--force-worktree-branches]` (`src/commands/gc.ts`; all git calls go through the injectable `GitRunner` seam in `src/lib/git.ts`) complements the runtime's own outcome-aware cleanup (the parallel-merge branch deletion and the external destroy hook's `PIPELINE_WT_DELETE_BRANCHES` — `1` only on a COMPLETED run that hasn't set `delete_branches: false` frontmatter; halted/depth-exhausted/create-failed always preserve) with an on-demand audit for the cases no runtime can cover (SIGKILL mid-run, a crashed hook, a manually deleted directory). The **report** (always printed, exit 0 even when leaks exist; exit 2 on usage / not a git repo) lists: registered git worktrees under `<project>/.claude/worktrees/` (`git worktree list --porcelain`) with each branch's merged state vs the default branch (`git merge-base --is-ancestor`; default = the `origin/HEAD` symref when resolvable, else `main`, else `master`); stale directories inside `.claude/worktrees/` NOT registered as worktrees (a dir that is a live worktree of a scanned submodule is NOT stale); prunable worktree records (`git worktree prune --dry-run -v`); and local `worktree-*` branches with no attached worktree, flagged merged/unmerged — with the explicit caveat that **squash-merged branches read as "unmerged"**, so orphaned branches are report-only and never auto-deleted unless provably merged. **Submodule scanning is ON by default** (`--no-submodules` to skip): runs provision worktrees in every declared submodule, so each crashed run historically leaked one `worktree-*` branch into EACH submodule repo (3,649 branches across ~30 submodules in the production consumer). Every initialized submodule (`git submodule status`; uninitialized ones are skipped silently and counted in `submodules_skipped`) gets the SAME scan against its OWN default branch (same ladder): orphaned `worktree-*` branches, registered worktrees whose path lies under the SUPERPROJECT's `.claude/worktrees/` (leaked registrations), and prunable records. **`--clean`** is CONSERVATIVE by construction: it runs `git worktree prune`, `git worktree remove --force`s only registered worktrees under `.claude/worktrees/` whose branch is fully merged (unmerged/detached/current ones are kept and listed with a reason), deletes the removed dirs' leftovers + other stale dirs, and `git branch -d`s (SAFE delete — never `-D`) merged branches that either match `worktree-*` or belonged to a worktree just removed; the same rules run per submodule (never the submodule's checked-out branch); it never touches the current branch/worktree and prints exactly what was kept and why. **`--force-worktree-branches`** (opt-in, requires `--clean`) additionally `git branch -D`s UNMERGED `worktree-*` branches — squash-merged run branches read as unmerged to `--is-ancestor` forever, so safe `-d` can never reap them; guard rails: only the machine-owned `worktree-*` namespace, never the current branch, and human output states how many were force-deleted per repo. `--json` emits one object `{default_branch, worktrees:[{path,branch,merged}], stale_dirs:[…], prunable:[…], branches:[{branch,merged}], submodules:[{path,default_branch,branches,worktrees,prunable}], submodules_skipped, cleaned:{pruned,removed_worktrees,kept_worktrees,removed_dirs,deleted_branches,force_deleted_branches,kept_branches,submodules:[{path,pruned,removed_worktrees,kept_worktrees,deleted_branches,force_deleted_branches,kept_branches}]}|null}` (pre-submodule fields unchanged); human mode prints a per-submodule section only for submodules with findings plus a one-line total ("N leaked branches across M submodules"), and a final "no leaks detected" line when everything is empty. Covered by `tests/gc-*.test.ts` (sharded; shared world in `tests/_gc-world.ts`) against REAL temp git repos (leaked merged/unmerged/detached worktrees, a deleted-dir prunable record, stale dirs, merged/unmerged orphan branches; report + `--clean` + idempotent re-run + the default-branch ladder + a superproject-with-submodule sandbox proving the merged/squash-unmerged/leaked-registration matrix, `--force-worktree-branches`, and `--no-submodules`). - **`pipeline ci-wait` is the token-efficient GitHub CI gate — block until CI reaches a terminal state, in ONE Bash call.** `pipeline ci-wait [--pr <number|url|branch> | --branch <name> | --sha <sha>] [--repo <path|owner/name>] [--timeout <sec>] [--interval <sec>] [--grace <sec>] [--fail-fast|--no-fail-fast] [--json] [--verbose]` (`src/commands/ci-wait.ts`; gh/git/clock/sleep all injectable — `tests/ci-wait.test.ts` scripts gh outputs poll-by-poll with a fake clock) exists because the LLM alternative is terrible: an agent poll loop (sleep → `gh pr checks` → read the table into context → repeat) burns a full agent turn per poll and, worse, agents have been observed waiting HOURS for full CI completion when one job already failed or hung. `ci-wait` polls `gh` IN-PROCESS, stays silent while waiting (`--verbose` opts into stderr heartbeats), and prints ONE compact result line (or one JSON object with `--json`). **Modes**: `--pr` covers a pull request via `gh pr checks --json name,state,bucket,link` (Actions + third-party checks/statuses; stdout is parsed regardless of gh's exit code, since gh exits non-zero while checks pend/fail); `--branch` resolves the branch HEAD sha ONCE at start via the API and then polls the commit check-runs endpoint for that pinned sha (a later push is a NEW gate, not a moving target); `--sha` skips resolution; NO selector = the repo's default branch (`gh api repos/{owner}/{repo} --jq .default_branch`). **`--repo` takes EITHER form and disambiguates by EXISTENCE FIRST**: an existing directory is a local path (it becomes the cwd of every gh subprocess, gh infers the repo from its origin — so a real directory literally named `owner/name` is never misread as a slug); otherwise a value matching `^[A-Za-z0-9._-]+/[A-Za-z0-9._-]+$` is a GitHub slug (what `gh --repo` itself means) and is written into every gh call — `-R owner/name` for `gh pr`, and straight into the endpoint path (`repos/owner/name/…`) for `gh api`, which has NO `-R` flag; anything else is a usage error that exits **2 immediately**, naming the value. (Before that validation existed, a slug passed to `--repo` made every `gh` spawn fail on a nonexistent cwd and the command burned the full grace period to report `no-checks`/exit 4 with `ENOENT … uv_spawn 'gh'` — "CI never started", the wrong operator action, from what is really a bad flag.) **Fail-fast is the DEFAULT**: the FIRST check landing in fail/cancel (or any non-passing terminal conclusion — unknown conclusions fail CLOSED) ends the wait immediately even while other jobs still run or hang; `--no-fail-fast` waits for the full picture; `--timeout` (default 1800s) caps stuck-forever CI and `--grace` (default 120s) bounds the "CI never started" case. **Exit codes**: `0` all passed (pass/skipping buckets; success/skipped/neutral conclusions) / `1` a check failed / `2` usage (bad flags, including a `--repo` that is neither an existing directory nor an `owner/name` slug) or gh missing/unauthenticated or unresolvable branch / `3` timeout (result lists the still-pending names) / `4` no checks appeared within the grace period — deliberately DISTINCT from success so a caller can never mistake "CI never started" for a green gate (an empty check list is grace territory, not a pass). The JSON result is `{status: success|failure|timeout|no-checks, mode: pr|commit, ref, sha, elapsed_s, polls, total, passed, failed, pending, failed_checks:[{name,state,link}], pending_checks:[names], detail}`. Intended use in iteration steps: a CI-gating step runs `bun "${CLAUDE_PLUGIN_ROOT}/apps/pipeline-cli/src/cli.ts" ci-wait --pr <n> --json` in a single Bash call (with the Bash timeout ≥ the `--timeout`) and branches on the exit code — no hand-rolled poll loops in step docs.
